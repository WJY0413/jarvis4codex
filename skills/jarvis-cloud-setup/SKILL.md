# Jarvis cloud setup

Use this for a new, isolated Linux cloud deployment. It does not authorize starting production work, changing global MCP registration, or moving credentials.

1. Select the exact reviewed distribution and record its archive hash, installed package version, source identity, dependency versions, configuration hash, and resolved runtime paths. Keep the previous release and its state untouched. A 0.3.0 engineering candidate is not a released version merely because the bundle has a 0.3.0 label.
2. Use an independently and officially logged-in Home on the target machine. If one already exists, verify and reuse it without requiring another login; otherwise an authorized operator must complete the official login flow. Never copy or print another Home's authentication files or platform tokens. Verify the actual `initialize.codexHome` equals the configured resolved Home; do not infer readiness from an environment variable or HTTP 200.
3. For the existing Linux cloud adapter, require `linux_cloud=true`, `runtime_environments=[]`, provider `openai`, read-only model sandbox, approval policy `never`, and a clean child environment. Before SDK startup, follow `CLOUD_COLD_START_GUIDE_REV6.md` section 3: load the candidate `NativeTaskLauncherConfig` and run its original `child_environment(cfg)` against the full unchanged parent environment; a guard error stops the probe. Only after success, pass existing candidate `SAFE_ENV` keys with unchanged values plus candidate-only `PYTHONPATH`/`PYTHONDONTWRITEBYTECODE`. Prevent the SDK default environment merge from adding other inherited keys, as shown in the guide's single-process recipe. Never clear parent routing to evade the guard, invent proxy/CA values, disable TLS, or read/copy authentication. Resolve configuration, project and executable paths on the target Linux filesystem; Windows drive and UNC paths are not portable.
4. Start only the separately authorized isolated TEST service using the versioned `python -m jarvis_mcp.entrypoint` arguments: `--config`, `--launcher-config`, `--state-dir`, and, when explicitly selected, `--transport streamable-http --port <loopback-port>`. The service is loopback-only; a public network route needs separate design and authorization. Do not edit a running release in place.
5. First run the guide's zero-model stdio cold start: 45-second total async deadline, 15-second `ClientSession` read timeout, exactly 17 tools, capabilities and loop preflight only. Preserve the SDK-owned TEST child cleanup and retain exit evidence; do not kill a shared Host. A timeout fails the probe. The canonical `source/tests/test_cloud_coldstart.py` verifies the guide with real stdio, environment filtering, pre-spawn guard rejection, and silent TEST child timeout/reaping. Only if separately authorized, proceed to one bounded synthetic model task through the intended public tool and record its request, real thread and turn, result bytes/hash, exact terminal status, Hold release, and cleanup. The zero-model cold start does not prove login, model routing, Schema intake, or release readiness; a staging AppServer turn does not prove a contact campaign or 30-seat workload.
6. If quota is below the user's 1% floor or official quota is exhausted, stop this rollout, retain receipts and report. Do not purchase credit, retry after reset, or silently continue. Unknown external execution, missing turn, or `closed_unconfirmed` remains unresolved; do not fabricate a terminal or dispatch a replacement.

The distribution must ship the adapted Jarvis Skill suite and a parameter audit alongside this setup Skill. Historical installed Skills are source inputs, not a compatible 0.3.0 suite until each claimed entry has been checked against the bundled MCP schema and representative behavior.
